# Architecture

How ResumeAI is put together, for developers joining the project. For setup and tuning see [SCALING_DATABASE_AUTH.md](SCALING_DATABASE_AUTH.md); for the scoring algorithms in depth see [PROJECT_REPORT.md](PROJECT_REPORT.md).

## Components

```
Browser (React SPA, Vite)
   │  Firebase ID token  or  workspace API key (rai_…)
   ▼
FastAPI backend (backend/app/main.py)
   ├─ auth.py / org.py ........ who is calling, which workspace
   ├─ routes/ ................. HTTP endpoints
   ├─ services/task_queue.py .. durable queue; workers run inside the API process or as `python -m app.worker`
   └─ services/ ............... parsing, verification, scoring, usage checks
   │
   ├─ MongoDB (Motor) ......... all state, including the task queue
   └─ External APIs ........... Gemini, Groq, GitHub, Firecrawl, Apify, DuckDuckGo, Composio
```

## Request flow: screening a batch of resumes

```
POST /api/v1/jobs/{job_id}/upload        save files, insert one `tasks` doc per file, return immediately
        │
task_queue dispatcher                      atomically claims queued tasks, runs RESUME_WORKERS in parallel,
        │                                  heartbeats, re-queues tasks whose worker died
        ▼
resume._parse_and_store                   text extraction → Gemini parse (bounded concurrency, retries)
        │                                  → section embeddings → de-duplicate → `candidates`
        ▼
unified_verification                      in parallel (asyncio.gather):
        │                                    GitHub v2 15-step authenticity pipeline
        │                                    LinkedIn lookup (Firecrawl → Apify fallback) vs. resume claims
        │                                    web search (DuckDuckGo)
        │                                  → `verification_data` with per-source status
        ▼
scoring                                   per-skill evidence scores + JD match + credibility
        │                                  → `applications` (one per job × candidate)
        ▼
GET /api/v1/jobs/{job_id}/tasks          progress the pipeline page polls
GET /api/v1/jobs/{job_id}/candidates     ranked list (3 queries regardless of size)
```

Interview questions (`GET /api/jobs/{job}/candidates/{candidate}/interview-questions`) are generated by Groq on first request and cached on the application. The fact checker (`POST /api/fact-checker/{candidate}`) answers questions from the resume and verification evidence.

## Authentication and workspaces

- Every `/api` route requires `Authorization: Bearer …`, either a Firebase / Google ID token verified against Google's signing keys, or a workspace API key (`rai_…`, looked up by SHA-256 hash).
- Each user has one active **workspace** (`users.org_id`). It is created on first sight; their earlier jobs move into it.
- Jobs carry `org_id`. `require_job_owner` / `require_candidate_access` (in `auth.py`) return 404 for anything outside the caller's workspace.
- Roles: owner, admin (invites, members, API keys), member. Invitations are single-use, expire after 14 days and only work for the invited email address.

## Data model (MongoDB)

| Collection | One document per | Key fields |
|---|---|---|
| `jobs` | Job posting | `org_id`, `owner_uid`, `status` (Active/Draft/Closed), `required_skills`, `jd_embedding` |
| `tasks` | Uploaded file | `job_id`, `status` (queued/processing/done/failed), `attempts`, heartbeat |
| `candidates` | Parsed resume | `candidate_id`, `parsed.personal_info`, `parsed.skills/education/experience`, `github_username`, `linkedin_url` |
| `applications` | Candidate × job | `status`, `score_details` (`jd_match_score` 0–10, `overall_score`, `skill_matches`), `interview_questions` |
| `verification_data` | Candidate | `verificationStatus` (github / linkedin / webCheck), source details, discrepancies |
| `evaluations` | Submitted interview | per-question covered points, total score |
| `users` | Person who signed in | `uid`, `email`, `org_id` (active workspace) |
| `orgs`, `org_members` | Workspace, membership | `name`; `org_id` + `uid` + `role` |
| `invites` | Invitation | `email`, `role`, `token`, `status`, `expires_at`, `email_sent` |
| `api_keys` | Workspace key | `key_hash`, `prefix`, `created_by`, `last_used_at`, `revoked_at` |

Indexes for every hot query are created at startup (`database.ensure_indexes`).

## Backend layout

| Path | Responsibility |
|---|---|
| `app/main.py` | App, CORS, router mounting, queue start/stop |
| `app/auth.py` | Token verification, API key sign-in, job/candidate access checks |
| `app/org.py` | Workspace resolution, roles, invitation email (Composio Gmail), key hashing |
| `app/routes/job_routes.py` | Job CRUD with candidate counts |
| `app/routes/resume.py` | Upload, task progress, candidate list, status changes, the parse → verify → score pipeline |
| `app/routes/org_routes.py` | Workspace, members, invitations, API keys, plan & usage |
| `app/routes/interview_questions_routes.py`, `evaluation_routes.py`, `fact_checker_routes.py` | Interview kit |
| `app/services/task_queue.py` | Durable MongoDB queue |
| `app/services/parser.py` | Gemini / langextract resume parsing |
| `app/services/unified_verification.py` | Runs and merges GitHub, LinkedIn and web verification |
| `app/services/github_services_v2/` | 15-step GitHub authenticity pipeline (matching, code/README similarity, behaviour, signal fusion) |
| `app/services/skill_matching/` | Evidence-weighted semantic skill scoring |
| `app/services/linkedinScraper.py` | LinkedIn lookup: Firecrawl `fullenrich/people/match`, Apify fallback |
| `app/services/usage_service.py` | Live limits of external API keys |
| `app/agent/` | Optional agent-based verification (`USE_AGENT_SYSTEM`, `DUAL_RUN`) |

## Frontend layout

See [frontend/README.md](../frontend/README.md) for routes, the shared UI kit and design tokens. In short: pages in `src/components/`, API clients in `src/services/`, theme and statuses in `src/lib/`. Every API call goes through `services/api.js`, which attaches the Firebase token; a 401 signs the user out.
